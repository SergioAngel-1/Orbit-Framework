# Headless Web Ecosystem v2.0.0: plan de implementación

> **Para agentes ejecutores:** SUB-SKILL REQUERIDA: usa
> superpowers:subagent-driven-development (recomendado) o superpowers:executing-plans para
> ejecutar este plan tarea a tarea. Los pasos usan casillas (`- [ ]`) para el seguimiento.

**Objetivo:** llevar el framework de v1.0 a v2.0.0 incorporando las correcciones, el contrato
de instancia y las funcionalidades genéricas validadas en Siu Tutuava, como plantilla sin
dependencias de ninguna instancia.

**Arquitectura:** portar archivo a archivo desde el HEAD de Siu, quitando lo específico de Siu,
en siete fases (F0–F6) que dejan el repo en verde. El núcleo expone un contrato de hooks y un
`InstanceRegistry`; la instancia vive en rutas reservadas que el framework nunca toca.

**Stack:**
- WordPress + WooCommerce headless (PHP 8.4, WPGraphQL/WooGraphQL, WC REST/Store API).
- Next.js 16 App Router + React 19 + TypeScript + Tailwind v4 + next-intl.
- Redis, Docker Compose y Caddy.
- Vitest y Playwright; PHPUnit + Brain Monkey (nuevos).

**Spec:** `docs/superpowers/specs/2026-10-12-hwe-v2-design.md`.
Contexto: `docs/superpowers/specs/2026-10-12-cruce-siu-framework.md`.

## Cómo leer este plan

- **Sin código literal.** Cada tarea dice qué lograr, de dónde se parte, dónde va, qué
  restricciones aplican y cómo se verifica. La implementación concreta es criterio del agente
  ejecutor, siempre dentro del spec, `AGENTS.md` y `CLAUDE.md`.
- **«Origen Siu»** es una ruta relativa al repo de Siu
  (`/home/sergi/Documentos/Proyectos/Siu Tutuava`) en el commit `d008bc15`. Lee el archivo de
  origen **completo** antes de portarlo; el docblock suele explicar el porqué. Si hace falta,
  consulta el commit citado con `git -C "<repo Siu>" show <sha>`.
- **Portar** significa traer el comportamiento y los tests de Siu y eliminar todo lo específico
  de Siu (nombres, slugs, copy, supuestos de catálogo o de país). Si algo de Siu contradice el
  spec, manda el spec.
- Las rutas de destino son las previstas. El agente puede partir un archivo en varios si eso
  mejora la claridad, y debe reflejarlo en el mensaje de commit.

## Restricciones globales

Aplican a todas las tareas.

- **Idioma:** documentación, comentarios y UI en español; código e identificadores en inglés.
- **Frontera núcleo/instancia** (spec §2):
  - el núcleo no importa `@/components/**` (salvo `ui/`) ni `@/instance/**` (salvo
    `@/instance/registry`);
  - el núcleo no contiene nombres de ninguna instancia.
- **Grep anti-instancia:** `siu|sheilak|mascota|essence|esencia|dormilab|atlas` (sin
  distinguir mayúsculas) debe dar 0 resultados en las rutas de núcleo. A partir de la tarea 25
  lo comprueba CI.
- **Seguridad:** secretos solo en el servidor (sin `NEXT_PUBLIC_`); `import "server-only"` en
  módulos sensibles; toda escritura en `/api/*` pasa por `guardMutation`. Ante la duda, la
  seguridad falla cerrada y el contenido de forma suave.
- **Sin fallos silenciosos:** todo error que se trague se registra con un `event` estructurado
  (pino en el frontend; `error_log` con prefijo `[hwe]` en WordPress).
- **Frontend:**
  - navegación desde `@/i18n/navigation`;
  - toda clave nueva en `es.json` va también en `en.json`;
  - clases de marca, nunca colores hex;
  - marca y URL desde `getSiteConfig()`;
  - importes de la Store API con `formatStoreAmount`;
  - HTML del CMS pasa por `sanitizeHtml`.
- **Módulos** (spec §8.4):
  - con `modules.<id> = false`, el lector devuelve vacío o nulo, las rutas BFF del módulo
    responden 404 y su UI no se pinta;
  - todo plugin de módulo registra su tag ISR en `hwe_revalidation_tags` y trae un
    `README.md` técnico y un `MANUAL.md` para editores, ambos neutros.
- **Versión:** v2.0.0 en un único salto. Los *breaking changes* se anotan al hacerlos en
  `docs/UPGRADE.md`, sección «v1 → v2», con una línea por cambio. La tarea 63 los redacta.
- **Commits:** Conventional Commits en español, con `Origen-Siu: <sha>[, <sha>…]` en el cuerpo
  cuando se porta. La rama de trabajo es `hwe-v2`. Termina el mensaje con:
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

### Batería V (verificación estándar)

Una tarea solo se cierra con la Batería V en verde, salvo que la tarea diga otra cosa.

1. Desde `frontend/`: `npm run lint`, `npm run type-check`, `npm run format:check`,
   `npm run i18n:check` (desde la tarea 4), `npm run test` y `npx next build`.
2. Desde `backend/`: `composer test` (desde la tarea 2).
3. Desde la raíz: el grep anti-instancia (desde la tarea 25).

Lo que necesite la pila WordPress real se declara **no verificado en vivo** en el informe de
la tarea, salvo que la tarea pida levantar la pila.

### Interfaces compartidas

Estos nombres son fijos. Las tareas que los producen y las que los consumen deben coincidir.

- Constante `HWE_CORE_CONTRACT_VERSION` = `'2.0.0'` (tarea 22).
- Filtros y acciones:
  - `hwe_control_center_schema` (filtro, array de schema);
  - `hwe_control_center_field_types` (filtro, mapa id → objeto que cumple `HWE\ControlCenter\FieldTypes\FieldType`);
  - `hwe_control_center_saved` (acción: `array $publicData, array $rawPost`);
  - `hwe_revalidation_tags` (filtro, lista de strings);
  - `hwe_modules_catalog` (filtro, mapa id → slug de plugin);
  - `hwe_translatable_fields` (filtro);
  - `hwe_geo_packs` (filtro);
  - `hwe_product_fields` (filtro);
  - `hwe_order_item_details` (filtro);
  - `hwe_integration_policy` (filtro);
  - `hwe_product_landing_icons` (filtro);
  - `hwe_banners_decor_presets` (filtro);
  - `hwe_shipping_free_rule` (filtro, ya existe en Siu).
- Interfaz `FieldType`, con tres responsabilidades: pintar el control, sanear el valor y
  declarar su persistencia (`config` | `secret` | `external`) (tarea 26).
- Cabecera interna `X-HWE-Internal-Secret` con el valor de `HWE_REVALIDATION_SECRET` (ya existe).

**TypeScript**
- `InstanceRegistry` (en `frontend/src/lib/instance/types.ts`): **solo datos**, nunca
  componentes de React. Contiene:
  - `revalidationTags: string[]` (tarea 24);
  - `landings`, con `staticEntries` y la declaración de `uniqueSections` (clave, `after`,
    `consumesBase`) (tarea 58);
  - `productFields` (tarea 60);
  - `decorPresets` (tarea 55).
- `instanceRegistry`: export de `frontend/src/instance/registry.ts`.
- `InstanceConfig`: interfaz vacía extensible en `lib/config/types.ts`; `SiteConfig.instance:
  InstanceConfig`.
- `ModuleId` (unión de los 9 ids del catálogo), `SiteConfig.modules: Record<ModuleId,
  boolean>`, `isModuleEnabled(config, id)` (en `lib/config/modules.ts`) y
  `requireModule(id)` (en `lib/api/modules.ts`, que devuelve una respuesta 404 o nada).
- Ids de módulo: `banners`, `shipping`, `product-landing`, `landings`, `consent-log`,
  `site-reviews`, `coupon-rules`, `customer-identity`, `external-integration`.
- `internalSecretHeaders()` (en `lib/security/internal-secret.ts`): cabeceras para toda
  llamada del BFF a WordPress (tarea 18).
- `getGeoPack()` (en `lib/geo/index.ts`), con tag ISR `geo` (tarea 52).
- `pickLocalized(entity, field, locale)` (en `lib/i18n/pick-localized.ts`), generalizado a N
  idiomas (tarea 51).
